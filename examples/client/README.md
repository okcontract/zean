# Set up a Zean client

A `zean.client.v1` manifest names the Zig source and capture roots, the
translation profile, and the generated module. It also lists dependencies,
proof modules, library imports, and theorem obligations. The cell example
proves a one-word write safe in a writable region of at least one word.
[Example manifest](client.json)

Try it from the Zean checkout with the standalone executable on your `PATH`.
This memory client uses AArch64 macOS AIR. [Standalone build](../../docs/toolchain.md#package-zean)

```sh
zean examples/client
zean examples/client --check
```

The module `Cell.Generated` goes to `lean/Cell/Generated.lean` inside the
target directory. Commit generated files with their Zig sources and proofs.
Zean replaces only files bearing its autogenerated header.

## Configure the project

Put `client.json` at the project root for one client. Use `zean.json` to list
clients in run order or choose a different Lean source directory.

```json
{
  "schema": "zean.project.v1",
  "clients": ["verification/cell.json", "verification/scan.json"],
  "leanDir": "lean",
  "sourceMap": {"verification/shared.zig": "src/shared.zig"}
}
```

Manifest paths, `leanDir`, and both sides of `sourceMap` are relative to the
project root. In each client manifest, source and proof paths are relative to
that manifest. Here the wrappers import `shared.zig` and list it in `sources`.
Zean captures the mapped `src/shared.zig` under the wrapper's import name.

The default `leanDir` is `lean`. Set it to `.` to write modules at the project
root. Give each client a unique `generatedModule`. You can leave both `proofs`
and `theorems` empty while writing contracts.

`zean --check` fails when a module is missing or stale. An unchanged source
closure and model keep the original capture hashes. Each run prints its
evidence path under `TMPDIR` or `/tmp`. Use `--evidence` to choose a fresh
directory. `--toolchain` selects a compiler report, and development builds
also read `ZEAN_TOOLCHAIN`.

## Check the proofs with Lake

Put `leanprover/lean4:v4.35.0` in `lean-toolchain`. With Zean checked out
beside the caller project, use this `lakefile.lean` for a `Cell` library.

```lean
import Lake
open Lake DSL

package cell_verification where
  leanOptions := #[⟨`warningAsError, true⟩]

require zean from "../zean"

@[default_target] lean_lib Cell where
  srcDir := "lean"
```

Place the handwritten proof in `lean/Cell/Proofs.lean` and update its path in
`client.json`. In `lean/Cell.lean`, import it and audit the named theorem.

```lean
import Cell.Proofs
import Compiler.ZigAir.ProofAudit

#audit_proof "Cell.safe" from ["Cell.Proofs"]
```

Run `LEAN_NUM_THREADS=2 lake build` to check the generated correspondence
theorems, the proof, and its axiom dependencies.

## Capture and replay in one command

Use the development target to check a client against fresh AIR and retain
the Lean receipts.

```sh
zig build verify-client -- \
  --manifest examples/client/client.json \
  --toolchain /path/to/toolchain/report.json \
  --output /tmp/cell-verification
```

Use a fresh evidence directory. Replay imports each generated or handwritten
module under a fresh name. Use one ordinary `import` per line and list
framework imports and earlier proof modules in the manifest. Replay requires
at least one named theorem, checks its module of origin, and allows only
Lean's standard logical axioms. Proofs run serially with a 4 GiB process
limit. Lake dependency builds use two workers. [Reports and scope](../../docs/evidence.md)

Call profiles emit the explicit call machine. `"executionModel": "call-machine"`
can assert that choice in a manifest. [Caller and helper example](calls/README.md)
